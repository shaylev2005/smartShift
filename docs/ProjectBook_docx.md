# 5. תקציר

SmartShift היא מערכת ווב לניהול ושיבוץ משמרות, שנועדה להחליף את תהליך השיבוץ הידני (לרוב באמצעות גיליונות אלקטרוניים) בכלי דיגיטלי מרכזי, מהיר והוגן. המערכת מיועדת לארגונים המנהלים כוננויות ומשמרות — כגון צוותי כוננות, מוקדים ויחידות — ומאפשרת למנהל לנהל לוחות משמרות, להגדיר את מצבת העובדים, לאסוף אילוצי זמינות מהעובדים ולשבץ אותם למשמרות. הבעיה המרכזית שהפרויקט פותר היא שיבוץ יעיל והוגן תוך התחשבות בו-זמנית באילוצי העובדים, בעומס השיבוץ המצטבר ובגיוון בין שבועות.

הליבה הטכנולוגית היא אלגוריתם **שיבוץ אוטומטי (Autofill)** המחשב הצעות שיבוץ על פי שלושה קריטריונים מדורגים: הימנעות מהפרת אילוצים, איזון עומס בין העובדים, וגיוון ביחס לשבוע הקודם. המערכת נבנתה בארכיטקטורת Next.js (App Router) עם בסיס נתונים Supabase (PostgreSQL), אבטחת מידע מבוססת הרשאות ברמת השורה (RLS), הפרדת הרשאות לפי תפקידים (מנהל / מפקד / עובד / אורח) ותמיכה במספר ארגונים במקביל (Multi-tenancy). המטרות שנקבעו — ניהול לוחות, איסוף אילוצים ושיבוץ אוטומטי מבוקר — הושגו במלואן, והתוצר הוא מערכת עובדת מקצה לקצה עם ממשק בעברית (RTL) ומצב כהה.

# 8. גוף העבודה

## 8.1 מבוא

### 8.1.1 רקע והמניע לפרויקט

בארגונים רבים המפעילים כוננויות ומשמרות (מוקדים, צוותי כוננות, יחידות תפעוליות), אחריות השיבוץ מוטלת על מנהל בודד המבצע אותה ידנית — לרוב באמצעות גיליון אלקטרוני. תהליך זה איטי, מועד לטעויות, וקשה לוודא בו הוגנות: קל לפספס אילוץ של עובד, לשבץ עובד מסוים יתר על המידה, או לחזור על אותה תבנית שיבוץ שבוע אחר שבוע. ככל שמספר העובדים והמשמרות גדל, מורכבות המשימה גדלה באופן לא-ליניארי.

הפרויקט **SmartShift** נולד מתוך הצורך להפוך תהליך זה לדיגיטלי, מרכזי ואוטומטי: מערכת אחת שבה העובדים מזינים את אילוצי הזמינות שלהם, והמנהל משבץ בלחיצת כפתור תוך התחשבות אוטומטית באילוצים, בעומס ובגיוון.

### 8.1.2 הגדרת הבעיה

הבעיה שהפרויקט פותר מורכבת ממספר אתגרים:

1. **ריכוז מידע** — אילוצי הזמינות של העובדים מפוזרים (הודעות, טלפונים, מסמכים) ואינם נגישים למנהל במקום אחד.
2. **שיבוץ תקין** — הימנעות משיבוץ עובד למשמרת שבה הוא אינו זמין.
3. **הוגנות ואיזון** — חלוקת עומס המשמרות באופן שוויוני, והימנעות מ"תקיעת" עובד באותה משמרת חוזרת.
4. **בקרת גישה** — עובד רשאי לנהל רק את האילוצים של עצמו, בעוד המנהל רשאי לשבץ ולצפות בכלל הנתונים.
5. **הפרדה בין ארגונים** — מספר ארגונים עשויים להשתמש באותה מערכת מבלי לראות זה את נתוני זה.

### 8.1.3 מטרות הפרויקט

- לספק ממשק לניהול **לוחות משמרות** (Boards) והגדרת מספר העובדים הנדרש לכל משמרת.
- לאפשר לעובדים להזין **אילוצי זמינות** — חד-פעמיים, מחזוריים (יום קבוע בשבוע) או לטווח תאריכים.
- לפתח **מנוע שיבוץ אוטומטי** המציע שיבוץ מיטבי, עם אפשרות למנהל לאשר, לערוך או לדחות כל הצעה.
- לאכוף **מודל הרשאות** מבוסס תפקידים ואבטחת מידע ברמת בסיס הנתונים.
- לספק ממשק משתמש נגיש בעברית (RTL) עם תמיכה במצב כהה.

### 8.1.4 סקירת פתרונות קיימים

קיימים בשוק כלים מסחריים לניהול משמרות (כגון When I Work, Deputy, Sling). כלים אלו עשירים בתכונות אך מאופיינים במורכבות, בעלות מנוי, ובכך שאינם מותאמים לעברית (RTL) ולתרחיש הישראלי של כוננויות. בנוסף, לוגיקת השיבוץ שלהם היא "קופסה שחורה" שאינה מאפשרת שליטה מלאה. SmartShift שם דגש על **פשטות, שקיפות אלגוריתם השיבוץ, והתאמה לעברית**, ומספק שליטה מלאה של המנהל על התוצאה (הצעה → אישור ידני).

- **Next.js + React** — מאפשרים לכתוב גם את הלקוח וגם את ה-API באותה קוד-בייס (Full-Stack) עם TypeScript משותף, ומספקים ביצועים טובים בזכות רינדור צד-שרת.
- **Supabase** — מספק "מגירה אחת" של בסיס נתונים יחסי (PostgreSQL), מנגנון אימות מובנה, והכי חשוב — **Row-Level Security (RLS)** המאפשר לאכוף הרשאות ברמת בסיס הנתונים עצמו, כשכבת הגנה נוספת מעבר לקוד.
- **TypeScript + Zod** — שילוב של בטיחות טיפוסים בזמן פיתוח (TS) ואימות קלט בזמן ריצה (Zod), הסוגר את הפער שבו נתונים חיצוניים אינם מובטחים.

### 8.2.2 ארכיטקטורה כללית

המערכת בנויה בארכיטקטורת שכבות ברורה, כאשר כל שכבה מדברת רק עם השכבה שמתחתיה:

**תרשים 1 — ארכיטקטורת השכבות:**

![](build/diagram1.png){ width=55% }

**עקרון מנחה:** נתיבי ה-API (`app/api/`) הם **"דקים"** — הם מאמתים הרשאות, מפרשים את הבקשה, קוראים לפונקציית שירות ומחזירים JSON. כל הלוגיקה העסקית מרוכזת בשכבת השירותים (`features/*/server/`). הפרדה זו משפרת תחזוקתיות ומאפשרת בדיקות יחידה של הלוגיקה במנותק מ-HTTP.

**מבנה מבוסס-תכונות (Feature-Based):** הקוד מאורגן לפי תחומים עסקיים ולא לפי סוג קובץ:

```
features/{assignments, constraints, profile, workers}/
  components/   # רכיבי UI ייעודיים
  contexts/     # ניהול מצב בצד הלקוח
  hooks/        # הוקים מותאמים
  server/       # פונקציות שירות (לוגיקה עסקית)
  types.ts
```

### 8.2.3 מודל הנתונים (בסיס הנתונים)

בסיס הנתונים כולל שבע טבלאות מרכזיות. אין שימוש ב-ORM — הגישה לנתונים מתבצעת ישירות דרך Supabase JS SDK.

**תרשים 2 — מודל הנתונים (ERD):**

![](build/diagram2.png){ width=95% }

**החלטות תכנון מרכזיות במודל:**

- **הפרדה בין `profiles` ל-`workers`:** משתמש רשום (`profile`) הוא ישות אימות, בעוד `worker` הוא ישות שניתן לשבץ. ההפרדה מאפשרת למנהל **להוסיף עובד למאגר עוד לפני שנרשם למערכת** (עובד עם `user_id = null`). כאשר העובד נרשם, המערכת מקשרת אוטומטית את הפרופיל שלו לרשומת העובד הקיימת.
- **`systems` (רב-דיירות / Multi-tenancy):** כל הטבלאות נושאות `system_id`, המאפשר למספר ארגונים לפעול על אותה מערכת בבידוד מלא.
- **`shift_boards` (לוחות):** לוח מגדיר תבנית שיבוץ — כמה עובדים נדרשים למשמרת (`workers_per_shift`), והאם המשמרת היא "יום שלם" (`single_person_for_day`).
- **`constraints` מחזוריים:** אילוצים שנוצרו יחד (מחזור שבועי או טווח) חולקים `recurring_group_id`, המאפשר מחיקה/עריכה של כל הסדרה בבת אחת.

### 8.2.4 מודל ההרשאות והאבטחה

המערכת מגדירה ארבעה תפקידים (`lib/utils/enums/role.ts`): **מנהל (manager)**, **מפקד (commander)**, **עובד (worker)** ו**אורח (guest)**. הפונקציה `canManage(role)` מחזירה "אמת" למנהל ולמפקד.

**טבלה 2 — מטריצת הרשאות:**

| פעולה | מנהל / מפקד | עובד | אורח |
|-------|:-----------:|:----:|:----:|
| צפייה בלוח המשמרות | ✔ | ✔ | ✔ |
| יצירה/עריכה/מחיקה של משמרות ולוחות | ✔ | ✖ | ✖ |
| שיבוץ עובדים למשמרות | ✔ | ✖ | ✖ |
| הפעלת שיבוץ אוטומטי | ✔ | ✖ | ✖ |
| ניהול אילוצים אישיים | ✔ | ✔ | ✖ |
| צפייה באילוצי כלל העובדים | ✔ | ✖ | ✖ |
| קידום עובד לתפקיד ניהולי | ✔ | ✖ | ✖ |

**אבטחה בשלוש שכבות (Defense-in-Depth):**

1. **Middleware** — כל בקשה ל-`/api/*` (למעט נתיבים ציבוריים כהרשמה) חייבת לשאת כותרת `Authorization: Bearer <token>`.
2. **שכבת האימות בקוד** — כל נתיב מוגן קורא ל-`requireUser()` (כל משתמש מאומת) או `requireManager()` (מנהלים בלבד) לפני כל פעולה. בנוסף, פונקציות `assert*Ownership()` מוודאות שהמשאב שייך לארגון של המשתמש.
3. **Row-Level Security (RLS)** — מדיניות ברמת בסיס הנתונים אוכפת, למשל, שעובד יכול לקרוא/לערוך רק את האילוצים שבהם `worker_id = auth.uid()`, גם אם שכבת הקוד תיכשל.

**אמצעי אבטחה נוספים:**
- **הגבלת קצב (Rate Limiting)** על נקודות קצה רגישות (הרשמה: 5 בקשות/דקה; שיבוץ אוטומטי: 10/דקה) בעזרת Upstash Redis, עם נפילה חלופית לזיכרון מקומי בסביבת פיתוח.
- **Content-Security-Policy** וכותרות אבטחה (X-Frame-Options: DENY, HSTS, nosniff) המוגדרות ב-`next.config`.
- **הודעות שגיאה בטוחות** (`lib/utils/errors.ts`) — חושפות רק שגיאות מבוקרות, ומחזירות "שגיאת שרת פנימית" לכל השאר, כדי לא לדלוף פרטי מימוש.

### 8.2.5 אלגוריתם השיבוץ האוטומטי

לב הפרויקט הוא הפונקציה `computeAutofillProposals()` (בקובץ `lib/assignments/autofill.ts`). האלגוריתם הוא **חמדני (Greedy)** עם דירוג רב-קריטריוני: עבור כל משמרת שחסרים בה עובדים, הוא מדרג את המועמדים הזמינים ובוחר את המתאים ביותר.

**סינון מקדים** — מועמד נפסל אם:
- הוא כבר משובץ באותה משמרת, או
- הוא כבר משובץ למשמרת אחרת באותו תאריך (מניעת שיבוץ כפול ביום).

**דירוג המועמדים** — הנותרים ממוינים לפי שלושה קריטריונים לפי סדר עדיפות:
1. **אילוץ זמינות** — עובד ללא אילוץ "לא זמין" (`unavailable`) קודם לעובד עם אילוץ.
2. **עומס שיבוץ** — עובד עם פחות שיבוצים השבוע קודם (איזון עומס).
3. **גיוון** — עובד שלא שובץ לאותה משמרת/תאריך בשבוע שעבר קודם (מניעת שגרה).

### 8.3.3 שכבת השירותים (Business Logic)

הלוגיקה העסקית מרוכזת ב-`features/*/server/*.service.ts`. דוגמאות מרכזיות:

- **`assignments.service.ts`** — `getAssignmentsOverview()` שולף במקביל (בשלושה שלבים) את כל הנתונים למסך הראשי, כולל **סנכרון עובדים** אוטומטי: יצירת רשומת `worker` לכל פרופיל חדש בעל תפקיד עובד/מנהל, וסינון אורחים. כן: `createAssignment()` ו-`deleteAssignment()` הכוללות בדיקת בעלות ארגונית.
- **`autofill.service.ts`** — `previewAutofill()` מחשב הצעות (ללא שמירה), ו-`applyAutofill()` מבצע את השמירה: יוצר משמרות חסרות לפי הגדרת הלוח, מוחק הסרות ומכניס הוספות, באופן אטומי.
- **`constraints.service.ts`** — `createConstraint()` המפצל לשלושה סוגים: בודד, מחזורי (יום קבוע לאורך שנה), וטווח תאריכים (עם `recurring_group_id` משותף).
- **`profile.service.ts`** — `ensureProfile()` יוצר/מסנכרן פרופיל לאחר התחברות, כולל לוגיקת קביעת תפקיד (המשתמש הראשון בארגון הופך למנהל) וקישור העובד.
- **`workers.service.ts`** — ניהול מאגר העובדים, כולל מניעת מחיקת עובד המקושר למשתמש רשום.

### 8.3.4 שכבת הלקוח (Frontend)

ניהול המצב בצד הלקוח מבוסס על **React Context** עם מטמון ברמת המודול (module-level cache) השורד ניווט בין מסכים:

- **`ProfileContext`** — מחזיק את פרופיל המשתמש הנוכחי גלובלית, ומאזין לשינויי אימות (התנתקות / רענון טוקן).
- **`AssignmentsContext`** — טוען וממטמן את סקירת השיבוצים, עם עדכונים אופטימיים (Optimistic updates) לאחר שיבוץ.
- **`ConstraintsContext`** — מנהל את רשימת האילוצים ואת חברי הארגון (למנהל).

כל קריאות ה-API מהלקוח עוברות דרך `lib/api/apiFetch.ts`, העוטף `fetch` ומצרף אוטומטית את ה-JWT.

### 8.3.5 מסכי המערכת

> **הערה:** להוסיף כאן צילום מסך לכל מסך (תמונה 1–5).

1. **מסך התחברות / הרשמה** (`/login`, `/signup`) — בהרשמה בוחר המשתמש ארגון וסוג משתמש (כונן רגיל / כונן במילואים / אורח).
2. **לוח המחוונים (Dashboard)** (`/dashboard`) — תצוגה שבועית של המשמרות (יום/לילה), סטטיסטיקות אישיות, ניווט בין שבועות, וסימון סטטוס מילוי בצבעים (ירוק=מלא, כתום=חלקי, אדום=ריק).
3. **מסך השיבוצים** (`/assignments`) — מסך הניהול המרכזי: תצוגת לוח שבועי או רשימה, שיבוץ עובדים בלחיצה, יצירת משמרות ולוחות, וכפתור השיבוץ האוטומטי הפותח חלון תצוגה מקדימה.
4. **מסך האילוצים** (`/constraints`) — יצירת אילוצים (בודד/מחזורי/טווח), סינון לפי תאריך ועובד, ומחיקת סדרה שלמה.
5. **מסך הגדרות** (`/settings`).

# 9. סיכום, מסקנות והמלצות

## סיכום

הפרויקט השיג את מטרותיו: נבנתה מערכת ווב מלאה מקצה-לקצה לניהול ושיבוץ משמרות. המערכת מאפשרת ניהול לוחות ומשמרות, איסוף אילוצי זמינות מגוונים (חד-פעמי / מחזורי / טווח), ושיבוץ אוטומטי חכם המתחשב בו-זמנית בזמינות, בעומס ובגיוון — כשהמנהל שומר על שליטה מלאה באמצעות אישור ההצעות. המערכת נשענת על ארכיטקטורה שכבתית נקייה, מודל הרשאות מבוסס-תפקידים, ואבטחת מידע בשלוש שכבות (Middleware, קוד, RLS).

## מסקנות

1. **הפרדת שכבות משתלמת** — הפרדת ה-API הרזה משכבת השירותים הקלה על פיתוח, איתור תקלות והרחבה.
2. **RLS כשכבת הגנה שנייה** — אכיפת הרשאות בבסיס הנתונים עצמו מספקת ביטחון גם אם שכבת הקוד תיכשל.
3. **אלגוריתם שקוף עדיף על "קופסה שחורה"** — מודל "הצעה ואישור" מייצר אמון: המנהל מקבל את יעילות האוטומציה מבלי לוותר על שיקול הדעת האנושי.
4. **ההפרדה בין `worker` ל-`profile`** התגלתה כהחלטת תכנון חשובה, המאפשרת שיבוץ עובדים עוד לפני הרשמתם.

## המלצות להמשך פיתוח

- **עדכונים בזמן אמת** באמצעות Supabase Realtime (WebSocket) לעדכון מסכים מרובי-משתמשים.
- **התראות** (דוא"ל / הודעות) על שיבוץ חדש או התנגשות אילוצים.
- **שיפור האלגוריתם** — שקילת אילוצים "חלקיים" (partial) בצורה מדורגת, והוספת משקלים מתכווננים לקריטריונים.
- **בדיקות אוטומטיות** — הוספת מערך בדיקות יחידה (Vitest) לשכבת השירותים ולאלגוריתם השיבוץ.
- **ייצוא ואינטגרציה** — ייצוא ללוח שנה (iCal) וחיבור למערכות שכר/נוכחות.
- **דוחות וניתוח** — לוח מחוונים אנליטי (ניצולת עובדים, פערי כיסוי).
